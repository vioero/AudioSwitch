# AudioSwitch 代码审查报告

> 审查日期：2026-09-13
> 审查范围：`src/AudioSwitch/**`（19 个源文件）、`installer/`、`publish/`、`docs/`、`README.md`
> 构建验证：`dotnet build -c Release` → **成功，0 错误 0 警告**
> 代码规模：约 2,100 行 C# + 745 行 XAML

---

## 总体评价

代码质量**高于个人项目的平均水平**：模块拆分清晰（9 个 Service 各司其职）、COM 资源释放意识强、设置写入做了原子替换、单实例/多屏回退/热键冲突等边界情况都有处理，注释也写了"为什么这么做"。

主要问题集中在三点：

1. **有两处会真正影响功能的 bug**（智能过滤的正则写错、默认设备 COM 对象泄漏）；
2. **工程化缺失**——没有 Git 版本控制、发布参数没有落到 csproj、版本号手工维护在多处；
3. **死代码与双源状态**——`AutoStartEnabled` 字段只写不读、`HotkeyService.Unregister` 从未调用、自启动状态同时存在于注册表和 JSON。

下面按严重程度排列。标记含义：**P0** 必须修、**P1** 建议尽快修、**P2** 有空再改、**P3** 锦上添花。

## 一、功能缺陷（P0 / P1）

### 1.1 【P0】智能过滤的正则写错，导致黑名单大面积失效

**位置**：`src/AudioSwitch/Services/DeviceService.cs:291`

```csharp
lower = System.Text.RegularExpressions.Regex.Replace(lower, @"s+", " ").Trim();
```

**问题**：`s+` 匹配的是**字母 s**，不是空白字符。要匹配空白必须是 `\s+`（这里少了反斜杠——大概是写字符串时被转义吃掉了）。

**实际后果**：设备名里所有字母 `s` 被替换成空格，黑名单关键词随之失配：

| 设备名 | 归一化后 | 关键词 | 结果 |
|---|---|---|---|
| `Stereo Mix` | ` tereo mix` | `stereo mix` | ❌ **漏网，不再被屏蔽** |
| `Primary Sound Driver` | `primary ound driver` | `primary sound` | ❌ **漏网** |
| `Sound Mapper` | ` ound mapper` | `sound mapper` | ❌ **漏网** |
| `Speakers (Realtek)` | ` peaker (realtek)` | — | ⚠️ 名称被破坏 |

也就是说，**智能模式下"立体声混音"这类本该隐藏的设备会重新出现在列表里**——这正是这个功能存在的意义。同时 `IsVirtualOrMisc` 前面几行辛苦做的 `®`/`™`/全角括号归一化，被这一行全部抵消。

**修复**：

```csharp
lower = System.Text.RegularExpressions.Regex.Replace(lower, @"\s+", " ").Trim();
```

### 1.2 【P0】默认设备的 MMDevice 未释放，长期运行 COM 对象泄漏

**位置**：`src/AudioSwitch/Services/DeviceService.cs:173-174`

```csharp
try { defaultMicId = enumerator.GetDefaultAudioEndpoint(DataFlow.Capture, Role.Multimedia)?.ID; } catch { }
try { defaultSpeakerId = enumerator.GetDefaultAudioEndpoint(DataFlow.Render, Role.Multimedia)?.ID; } catch { }
```

**问题**：`GetDefaultAudioEndpoint` 返回的 `MMDevice` 同样是 `IDisposable`。同一方法里枚举出的设备都老老实实 `using (device)` 包着（注释还专门写了"修复 L4：MMDevice 为 IDisposable，必须逐个释放"），**唯独这两个漏了**。

**影响**：`StartAutoRefresh()` 每 5 秒刷新一次 → **每小时泄漏约 1,440 个 COM 对象**。程序定位是"长期挂托盘"，这恰好是 `docs/后续迭代规划.md` 里"内存复查（长期挂托盘不增长）"这条待办的核心风险点。

**修复**：

```csharp
try { using var mic = enumerator.GetDefaultAudioEndpoint(DataFlow.Capture, Role.Multimedia); defaultMicId = mic?.ID; } catch { }
try { using var spk = enumerator.GetDefaultAudioEndpoint(DataFlow.Render, Role.Multimedia); defaultSpeakerId = spk?.ID; } catch { }
```

### 1.3 【P1】快捷键循环切换的索引与列表长度可能不一致

**位置**：`src/AudioSwitch/MainWindow.xaml.cs:84-91`

```csharp
if (args.DeviceType == DeviceType.Microphone)
    MicrophoneList.SelectedIndex = (MicrophoneList.SelectedIndex + 1) % args.DeviceCount;
```

**问题**：`args.DeviceCount` 来自 `HotkeyManager` 在**后台线程**取的 `DeviceService.Microphones.Count`（快照），而 `MicrophoneList.SelectedIndex` 属于 **UI 线程**的 ListBox。二者中间只要发生一次热插拔或刷新，就可能错位。

**后果**：
- 设备数变少时 → `% args.DeviceCount` 的结果可能超出 ListBox 实际项数，赋值后 SelectedIndex 被 WPF 钳制或跳到错误设备；
- 设备数变多时 → 循环范围不完整，末尾几台设备永远轮不到；
- `SelectedIndex == -1`（无默认设备）时 → `(-1 + 1) % n = 0`，能工作但属侥幸。

**修复建议**：不要跨线程传 Count，直接以 UI 自身为准：

```csharp
var list = args.DeviceType == DeviceType.Microphone ? MicrophoneList : SpeakerList;
if (list.Items.Count == 0) return;
list.SelectedIndex = (list.SelectedIndex + 1) % list.Items.Count;
```

### 1.4 【P1】快捷键注册失败时，设置已落盘但快捷key未生效，状态不一致

**位置**：`src/AudioSwitch/Services/SettingsPanelManager.cs:237-238`

```csharp
SettingsManager.Save();   // 先写盘
_onRefreshHotkeys();      // 后注册；失败会回滚成旧组合
```

**问题**：`HotkeyService.UpdateHotkey` 在新组合被占用时会**回滚到旧组合并抛异常**（HotkeyService.cs:70-81）。此时设置文件里已经写成了新值，而系统里实际生效的是旧值。

**后果**：用户看到气泡提示"已恢复原快捷键"，但下次启动程序会再次尝试注册新的（被占用的）组合，再次失败——**用户以为设置成功了，实际每次开机都静默失败一次**。

**修复建议**：先注册、成功后再写盘；或注册失败时把 `SettingsManager` 回滚并提示用户。

---

### 1.5 【P2】托盘菜单每次重建都新建 Font，未显式释放

**位置**：`src/AudioSwitch/Services/TrayService.cs:106-114`（`CreateHeader`）

每次右键托盘图标，`RebuildTrayMenu` 会新建 2 个 `Drawing.Font`。旧菜单项虽然调用了 `Dispose()`，但 `ToolStripItem` 不保证释放外部传入的 `Font` 对象，存在 GDI 句柄缓慢增长的风险。

**建议**：把 Font 提成 `static readonly` 字段复用（窗体关闭时统一释放），或在重建时显式 `old.Font?.Dispose()`。

## 二、工程化（P1 / P2）

### 2.1 【P1】项目没有版本控制

```
fatal: not a git repository
```

仓库根目录不存在 `.git`，但 `.gitignore` 已经写好了（内容还挺规范）。这意味着**所有历史改动不可追溯**，也无法回滚、无法对比。考虑到代码里大量"修复 M1/M2/L4"的注释，说明经历过不少次迭代——这些过程全部丢失了。

**建议**：立刻 `git init` + 首次提交。另外补一个 `.gitattributes`（`* text=auto eol=crlf`），避免 Windows/Linux 换行符混用。

---

### 2.2 【P1】发布参数没有固化，构建不可复现

**问题**：`publish/` 目录里只有一个 917 KB 的 `AudioSwitch.exe`（说明用的是 framework-dependent + single-file 发布），但 `AudioSwitch.csproj` 里**没有任何 `PublishSingleFile` / `RuntimeIdentifier` / `PublishTrimmed` 配置**，也没有 `.pubxml` 或 `build.ps1`。

**后果**：换台机器（或清理 obj 后）执行 `dotnet publish`，产出的会是 `AudioSwitch.exe` + `NAudio.dll` + 一堆依赖文件的目录，而不是 README 承诺的"单个 exe 文件，双击直接运行"。

**建议**：把参数写进 csproj（或新建 `Properties/PublishProfiles/portable.pubxml`）：

```xml
<PublishSingleFile>true</PublishSingleFile>
<SelfContained>false</SelfContained>
<RuntimeIdentifier>win-x64</RuntimeIdentifier>
<IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>
<DebugType>none</DebugType>   <!-- 发布版不必带 pdb -->
```

并加一个 `build.ps1` / `build.bat` 一键完成 publish + 编译 ISS。

## 三、健壮性（P1 / P2）

### 3.1 【P1】异常被静默吞噬，出问题无从排查

`DeviceService.cs` 里有三处空 catch：

```csharp
try { defaultMicId = ...; } catch { }                    // :173
try { defaultSpeakerId = ...; } catch { }                 // :174
catch { return null; }                                    // :230  ReadDeviceCached
```

`ReadDeviceCached` 的 catch 更是**连日志都不打**——设备读不出来时，用户看到的是"列表里少了个设备"，日志里什么都没有。

**建议**：至少 `Logger.Warn(...)` 记录设备 ID 和异常，方便用户反馈问题时定位。

---

### 3.2 【P2】线程安全的小漏洞

| 位置 | 问题 |
|---|---|
| `SettingsManager.cs:61` | `Save()` 直接读 `_current` 而没走带锁的 `Current`，与 getter 的加锁策略不一致 |
| `MainWindow.xaml.cs:21` | `_isExiting` 被后台唤醒线程读取（`SetupWakeUpListener` 的 `while (!_isExiting)`），未标记 `volatile` |
| `MainWindow.xaml.cs:41` | `DevicesChanged` 在后台线程触发 → `Dispatcher.Invoke`；窗口已销毁时会抛异常（虽被 try/catch 兜住，但退出时会刷一堆日志） |

---

### 3.3 【P2】热插拔用 5 秒轮询，可用事件驱动替代

`DeviceService.StartAutoRefresh()` 每 5 秒重建一次 `MMDeviceEnumerator` 并全量枚举。对"长期挂托盘"的软件来说，这是常驻的 CPU 和 COM 开销，且响应有最多 5 秒延迟。

**建议**：改用 NAudio 的 `MMDeviceEnumerator.RegisterEndpointNotificationCallback`（底层是 `IMMNotificationClient`），设备插拔时系统主动回调，零轮询、零延迟。

---

### 3.4 【P2】单实例 Mutex 用了全局命名空间

`App.xaml.cs:15`：

```csharp
_mutex = new Mutex(true, "AudioSwitch_SingleInstance_Mutex", out bool createdNew);
```

不带前缀的命名对象落在 **Global\** 命名空间（会话全局）。多用户/多会话（如远程桌面、切换用户）场景下，**A 用户启动的实例会阻止 B 用户启动**。

**建议**：改为 `Local\AudioSwitch_SingleInstance_Mutex`（`EventWaitHandle` 同理）。

---

### 3.5 【P3】COM 签名依赖隐式行为

`DeviceSwitcher.cs:20-34` 的 `IPolicyConfig` 未标注 `[PreserveSig]`。当前代码依赖 CLR 的默认封送（把返回的 `int` 当 HRESULT 自动抛异常）再叠加 `Marshal.ThrowExceptionForHR`，能跑通但语义依赖隐式规则。

**建议**：显式加 `[PreserveSig]` 并自己判断 HRESULT，意图更清晰，也避免未来运行时行为变化。

## 四、打包与分发（P1 / P2）

### 4.1 【P1】安装程序静默开启开机自启动，与 README 承诺矛盾

`installer/AudioSwitch.iss:51`：

```ini
Root: HKCU; Subkey: "...\Run"; ValueName: "AudioSwitch"; ValueData: "\"{app}\AudioSwitch.exe\""
```

而 `README.md:47-49` 明确写着：

> **⚡ 开机自启动** — 提供开关，用户可自由选择是否开机自动启动 / **默认关闭，由用户手动打开**

**实际行为**：安装完就自动进开机启动项，且安装向导里没有任何提示或勾选项。属于"宣传与实际不符"。

**建议**：加一个 Task 让用户选：

```ini
[Tasks]
Name: "autostart"; Description: "开机自动启动 AudioSwitch"

[Registry]
Root: HKCU; ...; Tasks: autostart
```

---

### 4.2 【P1】管理员权限安装会把自启动写到错误的账户

`AudioSwitch.iss:16` 设置了 `PrivilegesRequired=admin`，但 `[Registry]` 写的是 **HKCU**。安装程序提权运行时，`HKCU` 指向的是**提权后的那个账户**（通常是管理员），而不是当前登录的普通用户。

**后果**：用普通账户登录后，**开机自启动项根本不存在**（或指向了管理员账户），功能静默失效。

**建议**（任选其一）：
- 把 `PrivilegesRequired` 改为 `lowest`（配 `PrivilegesRequiredOverridesAllowed`），程序只装到 `{localappdata}` 或用户目录；
- 或者保持管理员安装到 `{autopf}`，但**去掉安装期的 Run 注册表写入**，改由程序首次启动时按用户意愿写入。

第二个方案和 4.1 一并解决，推荐。

---

### 4.3 【P2】安装时无条件安装 58 MB 运行时

`AudioSwitch.iss:41` 每次安装都跑一遍 `windowsdesktop-runtime-8.0.30-win-x64.exe`（`/quiet`），不检查系统是否已有 8.0+。用户重装一次就多花几十秒，还可能出现"已安装更高版本"的提示。

**建议**：用 `[Code]` 段检测已安装的 Desktop Runtime 版本，满足条件则 `skipifsilent` 跳过。

---

### 4.4 【P2】没有代码签名

未签名的 exe 会触发 Windows SmartScreen 拦截，对"分享给他人使用"是硬伤。`docs/后续迭代规划.md` 里也有"发布多人时加新版本提示"的计划。

**建议**：若计划分发，考虑申请个人开发者代码签名证书；同时现在就可以加一个自动更新检查（读取远端 version.json 比对 csproj 版本）。

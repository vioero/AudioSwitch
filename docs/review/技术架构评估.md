## 一、架构总评

### 1.1 总体结论

**架构一句话：分层清晰、职责边界合理、主题方案正确，整体达到可发布质量；主要短板是「设置面板逻辑与 UI 元素强耦合」和「安装发布链路存在断点」。**

| 维度 | 评价 | 说明 |
|---|---|---|
| 模块划分 | ✅ 良好 | Models（3 文件纯数据）/ Core（1 个 COM 封装）/ Services（10 个单一职责服务）/ UI（3 Window）/ Themes（4 字典），五块边界清楚 |
| 职责边界 | ✅ 良好 | DeviceService=枚举+过滤+缓存+轮询；SettingsManager=持久化；HotkeyManager+HotkeyService=全局热键（编排/Win32 两层）；TrayService=托盘+菜单编排；ThemeService=换肤；SettingsPanelManager=抽屉交互；MotionService/SystemThemeWatcher=系统适配 |
| 依赖方向 | ✅ 无循环 | UI → Services → Core/Models；Services 间仅 TrayService→DeviceService、SettingsPanelManager→（经 MainWindow 委托）HotkeyManager；`DeviceService.ShouldShowDevice` 静态读 `SettingsManager.Current`（DeviceService.cs:305）是唯一的服务间静态耦合，可接受 |
| UI 与服务层耦合度 | ⚠️ 中 | 见 1.3 |
| 线程模型 | ✅ 正确 | 后台 `Task.Run` 刷新 + `_refreshing` 重入保护（DeviceService.cs:99）+ `_lock` 保护缓存与列表；UI 线程只读快照副本。唯一阻塞点见 P2-1 |
| 设计令牌与主题 | ✅ 优秀 | 见 1.4 |

### 1.2 组合根模式

`MainWindow`（524 行）承担组合根：持有全部服务、接线事件、转发 UI 事件。有"上帝窗口"倾向，但在此规模（单进程托盘应用）下是合理折中——避免了 MVVM 框架成本，服务本身可独立测试（33 个单元测试即证明）。**不建议引入 MVVM 框架**，但应防止 MainWindow 继续膨胀（当前 524 行仍在可控范围）。

### 1.3 最大耦合点：SettingsPanelManager ↔ UI 元素

`SettingsPanelManager` 直接持有 `FrameworkElement`（settingsPanel/overlay，SettingsPanelManager.cs:15-16）并操作 `TranslateTransform` 动画（:295, :315, :326-335），`Initialize/Save/Reset` 共接收 12 个 `RadioButton` 参数（:61-70, :203-209, :268-271）。这是 UI 逻辑侵入 Service 层的设计折中：

- **后果**：该管理器无法脱离 MainWindow.xaml 的具体命名元素测试；XAML 中重命名任何 RadioButton 都会编译期静默通过、运行期 `NullReferenceException`。
- **建议（不必现在做）**：若后续设置项继续增加，把"设置视图状态"提为一个小 VM（属性 + ICommand），管理器只面对 VM。当前 9 个设置项规模下维持现状可接受。

### 2.3 现有 33 个用例的有效性评估

**有效性（正面）：**

1. **打得准**：30/33 集中在设备过滤与排序——正是历史 P0 正则 bug（审查报告 1.1）的阵地。推演验证：若将 `DeviceService.cs:340` 改回 `@"s+"`，`DeviceFilterTests` 至少 3 例失败（`"Stereo Mix"` 的 s 被替换成空格导致漏匹配；`"Intel®  Display   Audio"` 的双空格不被归一化）——这套用例确实守得住该回归，不是摆设。
2. **无副作用、可重复**：不碰文件系统/注册表/COM/网络，43ms 跑完，CI 友好。
3. **边界意识好**：空字符串、空列表、未知 defaultId、离线默认设备、稳定排序同组原序都有用例（`DeviceSortTests.cs:92-105`）。

**有效性（局限）：**

1. **面太窄**：只覆盖 4 个 static 纯函数；产品主流程（改设置→保存→热键生效、插设备→5 秒内列表刷新、点设备→系统默认设备变更）完全依赖人工，没有任何自动化防网。
2. **可达性靠 `internal` + `InternalsVisibleTo`**（`AssemblyInfo.cs:5）：`ShouldShowDevice`/`SameDevices` 至今是 private，恰好落在测试盲区——"想测就得先改可见性"在抑制补测。
3. **hermetic 性脆弱**：`SettingsManager` 静态构造器启动即读 `%AppData%`（`SettingsManager.cs:12-20`）。当前 33 例侥幸不经过它（纯函数路径），但将来任何涉及设置的测试都会读真实用户配置文件。
4. `FormatHotkey` 仅 3 例，四修饰键全开、有修饰键无 Key、修饰键顺序等组合未覆盖。

## 三、缺口测试设计（按价值排序，共 8 项）

### G1【P0】SettingsManager 持久化三件套
- **测什么**：①保存→加载往返一致；②`settings.json` 为损坏 JSON 时 `Load()` 返回默认值且不抛异常；③旧版含已删除字段（`AutoStartEnabled`）的 JSON 静默忽略（**设置迁移兼容**，防 v1.0.x 用户升级后配置读取失败）；④`Save()` 中途失败不残留 `.tmp`（M9 原子写回归）。
- **怎么测**：前置小重构——把 `SettingsPath`(`SettingsManager.cs:12`) 改为 `internal static` 可注入，测试指向 `Path.GetTempPath()` 临时目录，finally 删除。
- **防什么回归**：原子写入/损坏回退逻辑被无声破坏 → 用户配置丢失或每次启动重置。这是当前**价值最高**的缺口：设置文件是唯一用户数据，坏了没有任何提示。

### G2【P0】`ShouldShowDevice` 三种 DisplayMode 行为矩阵
- **测什么**：All 模式全显示；UsbBluetoothOnly 只放行 USB/BTHENUM；Smart 模式外部总线全放行 + 黑名单杂项（Stereo Mix/显卡 HDMI/兜底端点）隐藏 + 用户虚拟声卡（VB-Cable/VoiceMeeter）显示。即把 `DeviceFilterTests` 的 23 例在"模式维度"再组合一遍。
- **怎么测**：前置——`ShouldShowDevice`(`DeviceService.cs:303`) private → internal，且把 `DisplayMode` 从"读 `SettingsManager.Current`"改为**方法参数**（配合 G1 的路径注入，或直接解耦），使测试不依赖全局设置。
- **防什么回归**：历史 P0（过滤正则）**同类 bug 复发**。它是两个已测函数的组合器，却恰好在测试盲区；智能过滤是产品核心卖点"列表干净"，改错代价最大。

### G3【P1】`SameDevices` 变化检测（三维比较）
- **测什么**：Id 相同但 `IsConnected` 不同 → false；仅 `Name` 不同 → false；顺序不同但集合等价 → true；数量不同 → false。
- **怎么测**：前置——`SameDevices`(`DeviceService.cs:74`) private static → internal static。零依赖纯函数，10 分钟可写完。
- **防什么回归**：M2/M4 修复回退——热插拔后在线状态切换、默认设备变化不触发 `DevicesChanged`，用户看到"插了设备列表不动"。

### G4【P1】Models 纯函数：`DeviceKinds.Classify/GetLabel` + `DeviceRowItem` 计算属性
- **测什么**：`Classify` 覆盖 USB/BTHENUM/VIRTUAL/HDAUDIO/HDMI 名称回退/Unknown 六个分支；`GetLabel` 全枚举中文标签；`DeviceRowItem.Subtitle`（`"USB · 已连接"`/离线 `"未连接"`）、`AutomationName`（默认态后缀 `"（当前默认）"`）、`IconGlyph`（麦克风/音箱字形映射）。
- **怎么测**：零重构零依赖，直接可测。
- **防什么回归**：v2.0 UI 副标题与无障碍标签错乱——`DeviceRowItem.cs:29-38` 是显示层唯一的数据组装处，主窗口和托盘菜单都消费它。

### G5【P1】热键录制校验纯函数化 + `FormatHotkey` 全组合
- **测什么**：①从 `HandleKeyDown`(`SettingsPanelManager.cs:131`) 提取 `static string? ValidateHotkeyCandidate(HotkeyModifiers mods, Keys key, HotkeyConfig other)`：无修饰键→错误文案、与另一个快捷键相同→错误文案、Esc→取消，三条规则各正反；②`FormatHotkey` 补四修饰键全开、单修饰键、有修饰键无 Key、Win 排在 Shift 后等组合（现仅 3 例）。
- **怎么测**：提取为纯静态函数（窗口事件层只做键盘状态采集），即可完整单测。
- **防什么回归**：M4 修复回退——录进非法快捷键或两个快捷键相同，导致全局热键行为不确定/互相冲突。

### G6【P2】`HotkeyService.UpdateHotkey` 回滚（集成测试）
- **测什么**：注册组合 A → Update 到 B 成功；先把 B 用 `RegisterHotKey` 恶意占用 → Update 抛异常且 **A 仍生效**（回滚验证）；构造回滚也失败 → 抛"请重启程序"。
- **怎么测**：xUnit + STA 线程创建隐藏 `HwndSource` 窗口拿真实 HWND；只用冷门组合（如 Ctrl+Alt+F13），不抢用户常用键；测试进程退出自动清理。
- **防什么回归**：M3 修复回退——用户改热键撞车后旧热键直接失效、快捷键整体失灵。这是用户可感知的 P0 级故障，且当前逻辑（`HotkeyService.cs:50-72`）无任何自动化防网。

### G7【P2】`ThemeService.IsDark` 纯分支 + `AutoStartService` 集成（带清理）
- **测什么**：`IsDark(Light)==false`、`IsDark(Dark)==true`（System 分支读真实注册表，不断言）；`AutoStartService`：`SetEnabled(true)` → `IsEnabled()==true` → finally `SetEnabled(false)` → `IsEnabled()==false`。
- **怎么测**：前者纯函数；后者 try/finally 写测试自己的键并清理，不留副作用。
- **防什么回归**：自启开关状态错乱重演（历史"注册表与 JSON 双源"问题）；主题判定分支写反导致深浅色颠倒。

### G8【P3】`DeviceSwitcher.SetDefault` 真机冒烟（脚本，**不入 CI**）
- **测什么**：枚举设备 → 切换 → 用 NAudio 或系统音量合成器验证默认设备已真实变更 → 还原原设备。
- **怎么测**：真机 PowerShell/手工冒烟脚本。
- **防什么回归**：切换功能整体失效。**严禁进自动化 CI**：会改变运行者系统的真实默认音频设备。
